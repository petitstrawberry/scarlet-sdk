# scarlet-sdk tooling contract

Reviewed against the current implementation on 2026-09-06. This records the
existing build-tool boundary for the coordinated 1.0 release; it does not
announce a release, select dependency locks, or certify a board configuration.
The implementation lives in [cargo-scarlet](../cargo-scarlet/src/main.rs) and
the [Limine plugin](../cargo-scarlet-plugin-limine/src/main.rs).

## Scope

`scarlet-sdk` supplies `cargo-scarlet` and image-generation plugins. It is not
the Scarlet native user-library API, the Scarlet Rust compiler, or ScarletUI.
The user-facing interfaces are the CLI and documented project/bundle formats.
The Limine plugin is distributed with its matching SDK implementation.

Package versions, manifest schema versions, kernel/user ABI versions, and
toolchain revisions are separate. A 1.0 SDK package does not imply a stable
Rust kernel-module ABI, arbitrary nightly compatibility, or a new manifest
schema. Preserve the documented valid inputs and meanings within this scope;
diagnostic wording, internal Rust functions, generated-source formatting,
cache keys, and image-stamp encoding are implementation details.

## CLI

- `new --project <name>` scaffolds a project-root BSP using the legacy
  `[kernel]` manifest form, not a preconfigured board or a `bsp/` directory.
  Linker scripts, actual target JSON paths, and the placeholder boot entry
  still require project-specific editing.
- `build --project <path>` generates module dependencies, builds the kernel,
  and attempts the kernel-symbol sidecar injection. `check` and `clippy`
  operate on the project's BSP; they do not build every image layer.
- `image --project <path>` builds the kernel and composes the declared images.
  `--no-build` skips the kernel build, not image-layer Cargo/script execution.
  `--kernel-elf` selects a kernel input; combine it with `--no-build` when
  reusing a prebuilt kernel.
- `run --project <path>` composes images and runs `[runner].command`.
  `--no-image` skips composition. Arguments after `--` are passed to the runner.
- `update --project <path>` refreshes BSP Cargo dependencies and resolves layer
  sources into `scarlet.lock`; it is not a complete image build.
- `new --lsm <name>` and `build --lsm <path>` are for loadable Scarlet modules.
  The latter requires `--target <target-json-path>` and produces a `.lsm`.
  `--output` is a directory to which the built module is copied. The old
  `--module` spelling is no longer accepted.

Except for the LSM alternatives, project commands require `--project`.
`--release` selects the release profile for build/check/clippy/image/run.
`--target` overrides the BSP build target; LSM builds specifically require
a target JSON file path. `clippy` accepts arguments after `--` for its child
command. The SDK is not a pass-through for all Cargo flags.

## Project and bundle manifests

`scarlet.toml` uses `schema_version = 2` and a `[project]` with a `name`.
Current projects use `[bsp]` (`path`, kernel `package`) and `[bsp.kernel]`
(`source`, `features`). The BSP owns its Cargo package, boot entry, linker
script, and `.cargo/config.toml` target configuration. The older `[kernel]`
form with `package`, `source`, `target_json`, and feature states remains readable.

Kernel sources accept local paths or Git source tables. `[bsp.kernel].features`
accepts either a list of enabled names or a table of boolean states. Explicitly
disabled features are checked against Cargo metadata; feature unification must
not silently enable them through another dependency.

`scarlet.local.toml`, when present, is merged over `scarlet.toml` before parsing
the typed manifest. Tables merge recursively, arrays append in declaration
order, and other values are replaced by the local value, including changes of
representation. Keep this file outside version control. It is not a second
dependency lock or a way to remove an earlier array element.

`[modules]` selects regular Rust library crates for static linkage through the
generated `scarlet-modules` crate. Each enabled crate exposes `force_link()`;
the BSP calls `scarlet_modules::force_link()`. These crates are distinct from
LSMs and do not require `module.toml` or the LSM build command.

Image sections live under `[images.<name>]`. They select `format`, `output`,
ordered `layers`, and explicit image `deps`; boot sections also accept
`cmdline` and `dtb`. GPT sections select already-built payloads via
`partitions`. Dependency cycles and unknown dependencies are errors. Declare
the appropriate dependency when one image consumes another image's output.

## Layers and sources

- `bundle`: expands a `bundle.toml` containing `[[layers]]` at the point of
  declaration, recursively. Local paths are relative to the declaring file.
  Git sources support `subdir` and `bundle` (default `bundle.toml`).
- `copy`: copies a local file/directory or a downloaded URL input to `to`.
  `template = true` enables the existing copy-template processing.
- `archive`: verifies the required SHA-256 before safely extracting `tar`,
  `tar-gz`, `tar-zst`, or `tar-xz`, with optional `strip_components`. The hash
  may be a single value or a table keyed by architecture. Missing architecture
  entries and checksum mismatches are errors.
- `cargo`: builds a package/bin from a local or Git source, optionally below
  `subdir`, with the selected `features` and `default-features`, and copies its
  binary to `to`. `replace = true` removes earlier Cargo layers with the same
  destination; it is not a general override of every layer kind.
- `script`: invokes `sh <source> <output-path>` from the project directory and
  installs the output at `to`. A named `output` can be reused when its recorded
  hash matches; this does not track every external input used by the script.
- `image`: copies a previously built named image to `to`.

Layer paths resolve relative to the manifest or bundle that declares them.
The supported templates are `{arch}`, `{target_triple}`, and `{project}`.
Later filesystem layers can replace earlier files. These rules do not make
untrusted bundle or script sources safe to execute.

## Lock files and caches

`scarlet.lock` records image sections, ordered resolved layers, package Git
revisions, input identities, and output hashes. `update` and image composition
write it. Image hashes/stamps support incremental packaging; a reused image
is not evidence that every external tool or script input is reproducible.

Git Cargo layers reuse a recorded revision when their source and build inputs
match the lock entry. Otherwise the source selector is resolved again. Git
bundles are expanded from their own manifest selector, so pin their `rev` for
reproducible bundle definitions; the expanded package lock is not a bundle lock.

`--locked` on project build/image/run retains the SDK's existing scope:

- Require archive-layer URL, destination, format, stripping, and hash inputs
  to match `scarlet.lock`; missing or changed archive entries are rejected.
- Skip the SDK's explicit BSP `cargo update` before building.
- Continue reusing matching package revisions through normal source resolution.

It does not make every manifest change an error, make image composition
read-only, or forward Cargo's `--locked` to every child process. In particular,
missing/mismatched Git package entries can still be resolved, and image
composition still writes its resulting lock. Each Cargo workspace's
`Cargo.lock` separately describes its transitive Rust dependencies. Release
staging must select a compatible set of project and Cargo locks.

Managed caches stay under `.scarlet/cache`: `git` for bundle/package checkouts,
`files` for downloaded inputs, `target` for package-root-isolated Cargo outputs,
and `cargo-home` for child Cargo's registry/Git state. Existing inputs are reused
where applicable; missing inputs can be fetched. `--offline` has been removed.
Neither caches nor `--locked` are network isolation. Scripts, hooks, runners,
plugins, and child Cargo commands execute as host processes with the caller's
authority; use only trusted project inputs.

## Images, plugin, and execution hooks

Built-in formats are `newc`, `ext2`, `gpt-ext2`, and `gpt`. `limine-uefi` invokes
`cargo-scarlet-plugin-limine`. Other format names are rejected; the current
implementation is not an arbitrary format-prefix plugin-discovery mechanism.
Filesystem/firmware tools remain host dependencies listed in the README.

The SDK sends one JSON request on the Limine plugin's stdin containing
`project_dir`, `section_name`, `format`, `arch`, `kernel_elf`, `initramfs`,
`output`, and `section`. The section carries `cmdline`, optional `dtb`, and
`packages` with local `source` and absolute FAT `to` paths. The plugin supports
`aarch64` and `riscv64`. Its process exit status reports success/failure; it
does not return a structured result on stdout. There is no protocol-version
negotiation: distribute the plugin and CLI as a matched SDK revision set.

`[hooks.post-image]` supplies `command` and optional `args`. After successful
composition and lock saving, the hook runs from the project directory with
`SCARLET_PROJECT_DIR`, `SCARLET_TARGET_TRIPLE`, and `SCARLET_PROFILE` (`debug` or
`release`). Relative hook commands resolve from the project directory; a
nonzero status fails the operation. There is no transaction rolling back images
or locks when a later hook fails.

The runner is also started in the project directory, with `SCARLET_RELEASE=1`
for release runs and the CLI's trailing arguments. It owns emulator/device
configuration. The SDK does not sandbox or terminate unrelated host processes.

Generated aggregation sources, staging trees, and image stamps under
`.scarlet/` are SDK-owned artifacts. The aggregation `.cargo/config.toml` is
initialized only when absent; keep project-specific configuration deliberate.
Preserve source manifests and select distributable locks rather than treating
a local cache or sibling-source override as a release input.
